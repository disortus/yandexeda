# Utils layer

## Назначение
`utils` — это технические вспомогательные классы без состояния, которые переиспользуются в разных местах.

Обычно здесь находятся:

- форматирование сообщений
- нормализация строк
- конвертации
- маленькие чистые helper-функции

---

## Что реализовано в проекте

### `EmailUtils`

- нормализует email (`trim + lowercase`)
- используется в `AuthService` и `UserService`

Зачем:

- единое правило обработки email
- меньше дублирования

### Что было перенесено из `utils`

`ValidationErrorUtils` раньше находился здесь, но после архитектурного аудита перенесён в `exception`, потому что он работает с `BindingResult`, `FieldValidationError` и API error contract. Это не универсальная утилита, а часть слоя обработки ошибок.

---

## Правила для utils

1. Обычно `final class` + приватный конструктор.
2. Методы чаще всего `static`.
3. Никакого состояния и побочных эффектов (по возможности).
4. Если логика становится бизнес-ориентированной — переноси в service/validator.

---

## Когда не нужно использовать utils

Не выноси в utils всё подряд.

Если это:

- бизнес-логика -> service
- доступ к данным -> repository
- инфраструктурный бин -> config

Utils — для небольших общих helper-функций.


---

## Актуализация после аудита

Раньше здесь лежал `ValidationErrorUtils`, но это было спорное архитектурное решение. После аудита он перенесён в пакет `exception`, потому что он работает не с универсальной бизнес-нейтральной логикой, а с форматом API-ошибок.

Что остаётся хорошим кандидатом для `utils`:

- `EmailUtils.normalize(...)`,
- простые pure-функции без Spring-зависимостей,
- маленькие форматтеры, которые не знают о домене и слоях приложения.

Что **не** стоит класть в `utils`:

- security filters,
- JWT services,
- exception mappers,
- business validators,
- repository helpers с доступом к БД.

Если класс зависит от Spring MVC, Security, JPA или конкретного DTO ошибки — это почти наверняка не `utils`, а часть соответствующего слоя.
