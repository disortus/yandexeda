# `src/main/resources` — подробная документация по конфигурации приложения

Этот файл подробно объясняет, как в проекте устроена конфигурация через `application.yaml`, профили (`dev`, `prod`, `test`), переменные окружения и зачем всё это нужно.

> Важная цель этого документа: не просто показать "что написать", а объяснить **почему так** и как это использовать в реальных проектах.

---

## 1. Что хранится в `src/main/resources`

Папка `src/main/resources` — это ресурсы приложения:

- `application.yaml` — главный конфиг Spring Boot,
- `messages.properties` (если есть) — тексты локализации,
- sql-скрипты и шаблоны (если добавляются),
- любые файлы, которые нужны приложению на runtime.

Spring Boot автоматически добавляет содержимое `resources` в classpath, поэтому конфиги оттуда читаются при старте.

---

## 2. Роль `application.yaml`

`application.yaml` — центральная точка настроек приложения.

В этом проекте через него задаются:

1. имя приложения,
2. активный профиль,
3. datasource (БД),
4. JPA/Hibernate параметры,
5. логирование,
6. JWT и security-параметры,
7. настройки Swagger/OpenAPI.

### Почему YAML, а не `.properties`

Оба формата поддерживаются. YAML удобнее, когда конфиг большой:

- лучше читается иерархия,
- проще группировать параметры по блокам,
- меньше визуального шума.

---

## 3. Как Spring читает настройки

В проекте включён импорт `.env`:

```yaml
spring:
  config:
    import: optional:file:.env[.properties]
```

Это значит:

- если рядом с проектом есть `.env`, Spring попробует его загрузить,
- если нет — приложение всё равно запустится (`optional:`),
- значения из `.env` подставятся в `${...}` placeholders.

Пример:

```yaml
server:
  port: ${SERVER_PORT:8080}
```

Если `SERVER_PORT` не задан — используется `8080`.

## 4. Профили: `dev`, `prod`, `test`

Профили в Spring Boot позволяют иметь разные настройки для разных окружений.

### Общая секция (без профиля)

Верхняя часть файла — общие настройки, которые применяются всегда:

- `spring.application.name`,
- `logging.level.*`,
- `app.jwt.*`,
- `app.security.*`,
- `springdoc.*`.

### `dev` профиль

Используется для локальной разработки.

- БД: PostgreSQL,
- `ddl-auto: update` (для обучения удобно, но в проде так нельзя),
- `show-sql` можно включать для отладки.

### `prod` профиль

Используется в реальном окружении.

- БД: облачный PostgreSQL,
- `ddl-auto: validate` (схема должна быть готова заранее),
- SQL-логи выключены.

### `test` профиль

Используется в автотестах.

- БД: SQLite,
- `ddl-auto: create-drop` для изоляции тестов,
- лёгкая конфигурация пула.

---

## 5. Почему в тестах SQLite

Ты попросил, чтобы тесты не зависели от облачной PostgreSQL. Это правильная практика для обучения и CI:

1. тесты не ломаются из‑за сети,
2. быстрее старт и выполнение,
3. детерминированная среда,
4. проще запускать в любом окружении.

Важно понимать:

- SQLite и PostgreSQL отличаются по SQL-диалекту,
- поэтому часть edge-case поведения может различаться,
- для критичных production-сценариев полезны отдельные тесты на PostgreSQL (например, через Testcontainers) — это следующий шаг развития проекта.

---

## 6. Почему параметры выносятся в env

Секреты и environment-specific параметры нельзя хардкодить в коде.

Примеры:

- JWT secret,
- пароль БД,
- URL облачной БД,
- CORS origins.

Плюсы env-подхода:

1. безопаснее,
2. одинаковый jar можно запускать в разных окружениях,
3. удобнее CI/CD,
4. легче ротация секретов.

---

## 7. `.env.example` и `.env`

В репозитории есть `.env.example` — шаблон обязательных переменных.

Рекомендованный поток:

1. скопировать `.env.example` в `.env`,
2. заполнить реальными значениями,
3. `.env` не коммитить (он в `.gitignore`),
4. для команды обновлять `.env.example`, когда добавляются новые параметры.

## 8. Подробно по ключевым блокам `application.yaml`

### `app.jwt`

- `issuer` — кто выпустил токен,
- `secret` — ключ подписи JWT,
- `access-token-minutes` — TTL access token.

Минимум для безопасности:

- длинный случайный secret (>= 32 байт),
- отдельный secret для каждого окружения,
- не хранить secret в git.

### `app.security` (CORS)

- `cors-allowed-origins`,
- `cors-allowed-methods`,
- `cors-allowed-headers`,
- `cors-exposed-headers`.

В production всегда сужай список origin до конкретных доменов фронта.

### `spring.datasource`

Основные поля:

- `url`,
- `username`,
- `password`,
- `driver-class-name`,
- `hikari.*`.

### `spring.jpa`

- `ddl-auto` — стратегия управления схемой,
- `show-sql` — печать SQL,
- `hibernate.dialect` — диалект.

---

## 9. Как правильно выбирать `ddl-auto`

Коротко:

- `update` — удобно в разработке,
- `create-drop` — удобно в тестах,
- `validate` — безопаснее для production,
- `none` — когда schema управляется миграциями.

Для production-уровня рекомендовано перейти на миграции (Flyway/Liquibase), где версия схемы фиксируется явно.

---

## 10. Частые ошибки и как их избежать

1. **Секреты в git**  
   Никогда не коммить `.env`.

2. **Один профиль на всё**  
   Обязательно разделяй dev/prod/test.

3. **Слишком широкие CORS настройки**  
   Не оставляй `*` в production.

4. **Неправильный driver/dialect**  
   Проверяй соответствие БД и Hibernate dialect.

5. **Случайные значения по умолчанию в проде**  
   Для критичных настроек лучше падать при отсутствии переменной.

## 11. Практические команды запуска

### Запуск в dev

```bash
SPRING_PROFILES_ACTIVE=dev ./gradlew bootRun
```

### Запуск в prod (пример)

```bash
SPRING_PROFILES_ACTIVE=prod ./gradlew bootRun
```

### Запуск тестов (автоматически профиль `test` в соответствующих тест-классах)

```bash
./gradlew test --no-daemon
```

---

## 12. Резюме

`application.yaml` — фундамент конфигурирования Spring Boot приложения.  
Через него ты отделяешь код от окружения, делаешь приложение переносимым, безопасным и удобным для сопровождения.

Для учебного проекта это особенно важно: правильная конфигурация с самого начала закладывает архитектурную дисциплину, которая потом масштабируется на боевые сервисы.
