# `unit` — unit-тесты

Unit-тест проверяет один маленький кусок логики максимально быстро и изолированно. В таких тестах мы обычно **не поднимаем Spring context**, не подключаем БД и не стартуем web server.

## Что важно в unit-тестах

1. Тест должен быть быстрым.
2. Зависимости заменяются mock-объектами (`@Mock`).
3. Проверяется поведение конкретного класса, а не всей системы.
4. Ошибка в unit-тесте должна быстро указывать на конкретную бизнес-логику.

## Подпапки

- `service/` — тесты сервисного слоя.
- `validator/` — тесты бизнес-валидаторов.
- `utils/` — тесты чистых helper-функций.

## Почему unit-тесты нужны даже при наличии integration/e2e

Integration и e2e показывают, что система работает вместе, но когда они падают, причина может быть где угодно. Unit-тесты дают более точную диагностику: если сломалась нормализация email, это должен показать `EmailUtilsTest`, а не большой e2e сценарий.

## Как выглядит хороший unit-тест

Хороший unit-тест обычно строится по схеме Arrange / Act / Assert:

1. **Arrange** — подготовить входные данные и поведение mock-зависимостей.
2. **Act** — вызвать тестируемый метод.
3. **Assert** — проверить результат или исключение.

Пример из `AuthServiceTest`:

- Arrange: создать `RegisterRequest`, настроить `PasswordEncoder`, `UserRepository`, `JwtService`.
- Act: вызвать `authService.register(request)`.
- Assert: проверить email, роль, password hash и token в ответе.

## Чего не должно быть в unit-тестах

В unit-тестах обычно не нужны:

- `@SpringBootTest`,
- настоящая БД,
- настоящий HTTP-сервер,
- реальные env-переменные,
- сложная подготовка application context.

Если тесту нужен Spring context, это уже integration/web/e2e уровень. Такое разделение делает тесты быстрее и понятнее.
